# Security posture

AM2 has three caller surfaces with separate authentication boundaries.

| Caller | Entry point | Authentication |
|---|---|---|
| Browser WebAdmin | `webadmin.am2-poc.com` → PHP | Server-owned PHP session |
| Admin Android app | WebAdmin `api_*.php` | Same PHP session through its cookie jar; CSRF on unsafe methods |
| Field Android app | `apiapi.am2-poc.com` → Node | Authenticated WebSocket application login |

## WebAdmin invariants

- Identity and role come only from the authenticated server session; request parameters cannot select an admin identity or elevate a role.
- `am2_csrf_require()` protects unsafe browser and Admin API operations.
- Successful login regenerates the session identifier. Session startup enables strict mode and hardened `HttpOnly`, `SameSite=Lax`, and HTTPS-aware `Secure` cookies.
- Login attempts are rate-limited in the application and at the edge.
- Branch-admin mutations require ownership checks. Destructive actions additionally verify that the intended row was affected before reporting success.
- A PHP `auto_prepend_file` guard runs before document-root scripts. Anonymous API requests receive `401`; browser navigation is redirected or refused, while login entry points remain reachable.
- Production and staging use distinct session stores: `/var/lib/php/sessions/am2` and `/var/lib/php/sessions/am2-staging`.
- Direct requests to internal bootstrap/guard files do not expose their implementation.

## Edge and internal boundaries

- Internal Node admin callbacks used only by WebAdmin are denied at the public edge and remain loopback-only.
- Public Node routes use an explicit CORS allowlist.
- API-key validation uses Node's constant-time comparison. PHP presents the protected key only to the loopback relay and does not compare it itself.
- Update manifest/APK routes are intentionally public. Their integrity boundary is the canonical URL, signer and SHA-256 validation, atomic publication, and `no-store`; they are not protected by WebAdmin session auth.
- Rendered logs and other untrusted fields use text-safe rendering rather than raw HTML insertion.

## Host-security configuration lifecycle

The PHP prepend, PHP SAPI configuration, Apache/Nginx virtual hosts, lane session-store declarations, and Cloudflare real-IP configuration are host state outside the backend runtime artifact.

Static host-security source is packaged deterministically and verified against an independent expected manifest. This source contract does not yet prove installed-host provenance. The remaining lifecycle is:

```text
root-owned materializer
→ syntax/config checks
→ protected installation receipt
→ installed-state verifier
→ rollback/reload rehearsal
→ periodic drift audit
```

Cloudflare range refresh is externally sourced data and requires its own timestamped source record, validated generated bytes, protected receipt, stale-data policy, rollback, and refresh audit.

## Remaining adjacent risks

- The relay and WebAdmin still overlap as writers on several operational/durable tables. Write ownership must be made explicit before a Laravel aggregate cutover.
- Staging and production still share the Redis server/host, deploy account, and runtime VPS. These are tracked minimum-separation/hardening blockers, not evidence that current application writable paths are identical.
- Installed host-security files may currently protect live traffic correctly without being bound to the latest source contract by a protected receipt. Behavior health and provenance are separate gates.
