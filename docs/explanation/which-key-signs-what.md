# Which key signs what, and why

Four signing keys exist across two Android repositories. This explains the shape
so the question does not get relitigated, and records one decision that is easy
to reverse by accident.

## The rule everything follows

Not "debug versus release". The question is:

> Does this artefact land on a device belonging to somebody else?

Android permits an install over an existing app only when the new package
carries the **same signature**. It does not care what the key is called — a
debug keystore holds a real private key. What matters is continuity, and
continuity only matters once somebody other than the person who built it is
holding the phone.

| Flavour | Package | Lands where | Key |
|---|---|---|---|
| `dev` | `com.am2.tik.dev`, `com.am2.admin.dev` | developer machines | per-machine debug key |
| `staging` | `…​.staging` | operator handsets, field testing | one shared key, CI secrets |
| `production` | `com.am2.tik`, `com.am2.admin` | every unit | permanent app identity |
| `play` | `com.am2.tik` | Play Store (Client only) | same permanent identity |

## Why dev deliberately has no shared key

The dev flavour uses a **different package name**, so a dev build never collides
with a staging or production install on the same handset. The only cost of
having no shared key is the occasional `adb uninstall com.am2.tik.dev` when a
developer changes machines. Seconds.

The cost of having one is a signing key in every clone and in the whole of Git
history, forever.

Committing a debug keystore is a normal and legitimate practice — plenty of
Android teams do it so everyone shares one debug signature. It is not a hack.
But it earns its place when a team **shares physical test devices**, and this one
does not. The trigger is shared hardware, not team size.

**Revisit if** a test handset starts being passed between people and the
uninstall becomes a real interruption. Then add it, for the dev flavour only,
and only once the repository is private. Never reuse it for staging: that key
reaches operators.

## Why staging has its own key, separate from the release key

Staging APKs reach operator handsets, so they need continuity. That means a key
that outlives the runner, which means the key must live in CI.

The release key must not. Putting the application's permanent identity on every
runner that builds a staging APK trades a recoverable loss for an unrecoverable
one. Losing the staging key costs one uninstall per tester. Losing the release
key costs a new package name.

Before this existed, every staging APK was signed by a debug key that the runner
generated and discarded, so no staging build could be installed over the one
before it and every round of field testing cost an operator their local state.

## Why the release key is also the Play app signing key

Play App Signing normally has Google generate an app signing key and re-sign
what you upload. That would give the Play build and the sideload build different
signatures for the same package — so a handset could not move between them
without uninstalling.

Sideload is the primary channel here, so the key is provided to Google rather
than generated by it ("Export and upload", via the PEPK tool). Google's own
documentation names this case:

> "If you want to use the same signing key across multiple stores, make sure to
> provide your own signing key when you configure Play App Signing, instead of
> having Google generate one for you."

The consequence is that this key cannot be reset by Play. Losing it means a new
package name, a new listing, and every user reinstalling from scratch.

Admin never goes to Play — it has no `play` flavour, builds no AAB, and updates
itself through the panel's own channel, which Play forbids. Its release key is
simply the signature every Admin handset sees.

## Half configured is the dangerous state

Unconfigured is fine: a developer without any key still builds and runs. But
hand Gradle a keystore path with no password and it attaches no signing config
at all — the release artefact comes out signed with the **debug** key. It
builds, it installs, and it is not a release. Nothing in the output says so.

Both `app/build.gradle.kts` files therefore fail at configuration time when some
but not all of the four properties are present, so the wrong state is loud where
it is set rather than discovered in an artefact that already shipped.
